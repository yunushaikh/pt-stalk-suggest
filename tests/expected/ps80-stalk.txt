Transactions and locks
----------------------------------------------------------------------------------------------------
  How to read this: InnoDB locks the rows a statement changes, and under REPEATABLE READ also the 
  rows (and the gaps between them) it reads to find them, until the transaction commits. A 
  statement that has to read a whole table to change one row therefore locks the whole table, and 
  everything else that writes to it waits.


  What waiting transactions are waiting for (SHOW ENGINE INNODB STATUS)
  Waiting            no transaction was waiting for a lock in the status snapshots

  Internal latch waits (SEMAPHORES)
        1 waits at log0meb.cc line 1782 (longest 0s): the redo log
    Meaning: threads queued on an InnoDB internal latch, a short-term lock on an in-memory 
    structure. Many waits in the same place show what is contended.

Caveats
----------------------------------------------------------------------------------------------------
  * ps shows 3 mysqld processes on this host: the memory budget assumes the largest one and counts 
    the others as other processes.
  * Could not match datadir to an iostat device; disk numbers use the busiest device (dm-0).
  * RAM comes from /proc/meminfo, which shows the host's memory even when mysqld runs in a 
    container or pod with a lower memory limit; pt-stalk does not record cgroup limits, so memory 
    suggestions assume the whole host is available.
  * pt-stalk captures a short window, often during an incident. Window rates show that moment; 
    settings should fit normal load with headroom for it, so compare with the 'since start' figures 
    before changing anything.
  * Not applicable here: query_cache (removed in 8.0)
