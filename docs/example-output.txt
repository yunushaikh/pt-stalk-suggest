Details (evidence and formulas)
----------------------------------------------------------------------------------------------------

  [CHANGE] innodb_redo_log_capacity   100M -> 1G   (confidence: High)
    Evidence   Redo written: 75.6M/s in window (peak 98.4M/s), 425.2K/s since start
               Capacity 100M (innodb_redo_log_capacity, default for 8.4: 100M) holds 1.3 s of
               writes at 75.6M/s
               Checkpoint age: max 83.3M of 83.3M = 100.0%; modified age 74.6%
               (Innodb_checkpoint_age, max of every sample)
               Flushing thresholds: aggressive from ~87.0%, sync flush (writes stall) from ~93.0%
               of max checkpoint age
    Formula    target = one hour of writes, at most max(buffer pool size, 2 x current) and 512G:
               checkpoint age reached the aggressive-flushing zone
    Why        InnoDB reached 100.0% of the max checkpoint age: it flushes pages furiously (and
               stalls writes above ~93%) to free redo space. Dynamic since 8.0.30: SET PERSIST
               innodb_redo_log_capacity = 1073741824;

  [CHANGE] table_open_cache   4000 -> 8000   (confidence: Medium)
    Evidence   Opened_tables: 752/s in window (peak 1046/s), 4.02/s since start
               Open_tables: max 1235 of table_open_cache 4000 (default for 8.4: 4000) (30.9%);
               instances 16
               Cache miss rate in window: 7.5%; overflows 752/s
               Per instance: 4000 / 16 = 250 tables; a session always uses instance thread_id % 16,
               and most reopens are overflows of one instance
    Formula    new = 2 x current (rounded to 500), repeat until Opened_tables/s is near 0; requires
               open_files_limit >= 10 + max_connections + 2 x table_open_cache = 16210
    Why        Tables are evicted from a full instance while the cache as a whole is not full:
               sessions touch more tables than one instance holds. Raise table_open_cache (dynamic)
               so table_open_cache / instances covers the tables a busy session uses, or lower
               table_open_cache_instances (needs a restart).

  [CHANGE] open_files_limit   8210 -> 17000   (confidence: Medium)
    Evidence   Open_files: max 14 of open_files_limit 8210 (0.2%)
               Needed for max_connections 200 and table_open_cache 8000: 10 + 200 + 2 x 8000 = 16210
    Formula    new = max(10 + max_connections + 2 x table_open_cache, 1.5 x Open_files), rounded to
               1000
    Why        Too low for the table cache (or close to exhausted). Not dynamic: set LimitNOFILE in
               the systemd unit (or ulimit -n) and open_files_limit, then restart.

  [CHANGE] binlog_cache_size   32K -> 128K   (confidence: Medium)
    Evidence   Binlog_cache_disk_use / Binlog_cache_use: 99.3% in window (7.07 trx/s), 90.7% since
               start
               Statement cache spills: 0.0% since start
    Formula    new = 4 x current (power of 2), at most 4M
    Why        More than 10% of transactions spill their binlog events to a temporary file. The
               cache is allocated per connection only when it writes, so a few MB is affordable.
               Dynamic.

  [REVIEW] innodb_io_capacity / _max   10000 / 20000 -> fix redo first   (confidence: Low)
    Evidence   Pages flushed: 4514/s in window (peak 6378/s) vs io_capacity 10000 / io_capacity_max
               20000 (defaults for 8.4: 10000 / 20000)
               Dirty pages: max 29.99% of the pool (innodb_max_dirty_pages_pct = 90)
               Redo pressure: 100.0% of max checkpoint age (aggressive flushing from ~87.0%)
               Disk dm-0 (busiest): w/s avg 11357.2 max 16630.0; r/s avg 166.0; %util avg 74.2 max
               85.4; w_await avg 1.17 ms
    Formula    re-evaluate after the redo log change
    Why        The flushing pressure comes from a redo log that is too small. Sync flushing is not
               limited by io_capacity_max (buf0flu.cc: it flushes up to 2 x io_capacity_max per
               pass without sleeping), so raising io_capacity does not help here. Resize the redo
               log, take a new capture, then revisit io_capacity.

Caveats
----------------------------------------------------------------------------------------------------
  * ps shows 3 mysqld processes on this host: the memory budget assumes the largest one and counts
    the others as other processes.
  * Could not match datadir to an iostat device; disk numbers use the busiest device (dm-0).
  * RAM comes from /proc/meminfo, which shows the host's memory even when mysqld runs in a
    container or pod with a lower memory limit; pt-stalk does not record cgroup limits, so memory
    suggestions assume the whole host is available.
  * pt-stalk captures a short window, often during an incident. Window rates show that moment;
    settings should fit normal load with headroom for it, so compare with the 'since start' figures
    before changing anything.
  * Not applicable here: query_cache (removed in 8.0)
